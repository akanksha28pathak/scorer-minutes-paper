## Abstract

Coding-agent benchmarks increasingly limit each session by wall-clock time, as this competition does (a per-session
cap, a 12-hour total, 4x NVIDIA L4). A wall-clock cap silently mixes what the agent does with how fast the GPU decodes:
teams develop on other hardware and at other concurrency, where the same cap buys a different amount of model work. We
release **scorer-minutes**, a small, dependency-free toolkit and protocol that (1) converts wall-clock budgets between
setups with a single speed factor measured from standard per-call logs, (2) checks from the same logs whether one
factor is enough, and (3) reports run-to-run noise and what it implies for comparisons and single leaderboard draws.
Across 81 logged runs (3,513 sessions) of Gemma 4 agents on five GPU types, per-session speed for the same 31B model
ranges from 14 to 38 tokens/s, a 2.7x spread, and Kaggle's own 4x L4 hardware is **2.0-2.3x** slower per session at
10 concurrent sessions than when it scores one at a time. Evaluated at the nominal cap there, one agent solved **4/10**
tasks; with the cap scaled up, **9/10**. Model time is 96-100% of every session and prefill 1-6% of model time, so one
factor suffices. The conversion reproduces a reference result on a different GPU (19 vs 17 of 55, within noise)
**[L4: and on a 2x slower setup]**. Identical runs differ with a pooled SD of **1.2-1.6 tasks of 55**: a 2-task
difference measured once is ranked wrongly about one time in five, and 11 runs per agent are needed to detect it
reliably. We release the toolkit, the per-run speed and timing table, the repeated-run matrix, and a one-page protocol.

## 1. Introduction

This competition scores an agent (prompts, tools, optional LoRA) on about 120 hidden tasks from
private repositories: each session runs under a per-session cap set by the submitter, all sessions must finish within
12 hours on 4x L4 (tensor parallel 4, vLLM 0.19.1, tasks run one at a time), and the score is the share of tasks whose
tests pass.

Nobody develops on the scorer. Teams test on rented A100s, workstation GPUs, or Kaggle's own 4x L4 with many sessions in
parallel to save quota. Each setup decodes at a different speed per session, so the same "7 minutes" is a different
budget on each. We found this the hard way: our first 31B agent looked weak in local tests (4/10) because ten sessions
shared the GPUs, each decoding at about 15 tokens/s instead of the scorer's ~34; given the scorer's effective budget it
solved 9/10 (Section 4.2). The reverse error is as costly: a budget tuned on a fast machine overruns the 12-hour limit
on the scorer, and an overrun scores zero.

A second problem compounds the first. Agent runs are noisy: sampling, scheduling and timing make the same agent solve
different tasks on every run. Single-run comparisons and the public leaderboard rarely report this noise, so
differences of one or two tasks are read as progress.

**Contributions (the resource).**
1. `scorer-minutes`, a toolkit (Python standard library only; commands `calibrate`, `timing`, `noise`, `draws`) that
   reads OpenAI-style per-call logs and outputs the speed factor, the equivalent wall cap, a prefill / decode / tool
   time split, run-noise estimates and power calculations (Section 3).
2. A per-run table of speed, factor and time split for 81 runs of Gemma 4 31B, E4B and a 26B-A4B teacher on seven
   setups (Section 4.1, `docs/paper/aggregates/speed_table.csv`).
3. A repeated-run matrix (55 tasks x 15 full runs, solved or not) and the noise table derived from it (Section 5).
4. A one-page protocol for reporting time-budgeted agent results (Section 6).

## 2. Related work

**Time-budgeted agents.** Wang et al. [On the Clock, arXiv 2610.10833, NeurIPS 2026 Workshop on Resource-Aware Agentic AI] study whether
small LLM agents respect a wall-clock budget and use extra time well (MLE-Bench Lite, Zork); agents told the budget only
in the prompt overrun it, and exposing a clock in the harness fixes this. That work is about the agent's behavior under
a fixed clock; ours is about what the clock means on different hardware. Benchmark papers that report wall-clock time
treat it as a within-environment diagnostic [OpenHarmony Bench, arXiv 2608.16022], or give all agents the same
wall-clock limit without normalizing it [AnalysisBench, arXiv 2604.11270]. We know of no protocol that converts a wall-clock cap between setups.

**Evaluation noise.** Miller [Adding Error Bars to Evals, arXiv 2411.00640] gives standard errors, paired
comparisons and power analysis for LLM evals. For agents, "On Randomness in Agentic Evals" [arXiv 2602.07150] finds single-run pass@1 on SWE-bench Verified shifting by 2.2-6.0 points across runs (SD > 1.5 points even at
temperature 0) and recommends multiple runs and power analysis. HAL [arXiv 2510.11977] builds
reproducible, cost-aware agent evaluation infrastructure. We apply the same statistics to a time-budgeted setting,
measure them on a live competition (local runs and leaderboard), and package them with the speed normalization, since
the two interact: a budget change moves scores by about as much as run noise.

**Concurrent work in this competition.** Public paper-track notebooks measure 31B decode speed on one L4 at one
concurrency [P. D. Pereira, "L4 Decode Law & 12-Call Cliff"], leaderboard noise from resubmitted files
[D. Afshar, "58 Tasks, Bronze Is a 124-Team Tie"], and time and context feasibility of submission configs
[V. Murugan, "Budget Feasibility Audit"; netaro, "YaoNeM Pareto Analysis"]. None converts a cap between setups,
validates a conversion with a control, or measures local repeated-run noise; we reuse their leaderboard figures.

**Agent workloads.** TraceLab [arXiv 2606.30560] characterizes ~4,300 Claude Code and Codex sessions for LLM serving:
long contexts with short outputs, heavily tailed tool calls and high but imperfect prefix-cache hit rates. Our setting (an open 31B model at 32k context, a sandbox with fast tools)
is the opposite case; we measure where the time goes rather than assume it (Section 4.4).

## 3. The resource

### 3.1 Definitions

For each session *s* of a run, from its per-call logs:

* session speed `v_s = completion tokens / time inside model calls` (prefill included: it is the throughput the agent
  gets per second of model time, the quantity a time cap rations);
* run speed `v = median_s v_s` (robust to stalled or very short sessions), with a bootstrap CI over sessions;
* **factor** `f = v_ref / v` (f > 1: slower than the reference);
* **scorer minutes** of a session `= wall minutes / f`; the wall cap equal to a budget of *B* scorer minutes is `B x f`.

`v_ref` should be measured on the scoring setup at its real concurrency (`calibrate --reference`). For this
competition the scorer runs one session at a time on 4x L4 (TP4). A logged sequential run there measured **33.8
tokens/s** per session (5 sessions, IQR 32.8-34.4). For our development runs we used 31.6 tokens/s, the speed of an A100
80 GB at 5 concurrent sessions, which matched an earlier unlogged sequential check (~32); across 15 full A100 runs the
median was 30.4 (range 29.2-32.2). The A100 proxy is therefore 6-10% slower than the direct anchor, so our "7
scorer-minute" budgets were slightly generous; the toolkit makes such offsets visible instead of silent. Factors below
are against 31.6, as used for the runs; against the direct anchor they are 7% larger.

### 3.2 When one factor is enough

A single factor converts budgets only if session time is dominated by model calls running at a roughly constant
speed. `timing` checks this from the same logs:

* **model share** of wall time per session (tools, sandbox and harness are the rest);
* a per-call least-squares fit `t = c + a * new_prompt + b * gen + d * gen * context` (tokens in thousands), splitting
  overhead, prefill (only tokens added since the previous call, as with prefix caching) and decode, with decode slowing
  as the context grows;
* model-free checks: tokens/s per context bin and early vs late calls of each session;
* flags for sessions with model share < 0.9 or prefill share > 0.2.

### 3.3 Noise

`noise` takes `config, split, run, task, solved` rows and reports per-config SD, the pooled SD over configs with >= 2
runs, a task-level SD (each task an independent coin with its observed solve rate, which uses all tasks rather than a
handful of run totals), difference CIs (run noise and a task bootstrap), the runs needed to detect a margin (alpha 0.05,
power 0.8), and the chance that one run each ranks two agents in the wrong order. `draws` does the same for single
leaderboard scores.

### 3.4 Design

Python standard library only (runs on a laptop, a Kaggle kernel or a GPU box without installs); field names are
configurable dotted paths, so OpenAI, LiteLLM and vLLM logs work unchanged; deterministic (seeded bootstrap); 14 tests
on synthetic logs with known prefill and decode speeds, which the fit recovers exactly. Code: `tools/scorer_minutes/`;
repo adapters `analysis/speed_table.py`, `analysis/noise_table.py`; one script regenerates every table.

## 4. Validation

Runs: Gemma 4 agents in the competition's harness and sandbox image, strict grading as the scorer, vLLM serving.

### 4.1 Speed depends on the GPU and on concurrency

Full runs (>= 20 sessions) grouped by setup; tokens/s = median per-session speed of each run.

| Setup | Model | Concurrent sessions | Runs (sessions) | Tokens/s per session (range over runs) | Factor vs 31.6 |
|---|---|---|---|---|---|
| Kaggle 4x L4, TP4 (scorer hardware) | 31B | 1 | 1 (5) | 33.8 | 0.94 |
| A100 80 GB | 31B | 5 | 15 (911) | 30.4 (29.2-32.2) | 1.04 |
| A100 80 GB, + LoRA adapter | 31B | 5 | 1 (55) | 26.1 | 1.21 |
| RTX PRO 6000 Blackwell 96 GB | 31B | 5 | 11 (693) | 38.3 (37.6-38.6) | 0.83 |
| Kaggle 4x L4, TP4 | 31B | 10 | 4 (151) | 14.4 (14.0-15.8) | 2.0-2.26 |
| Kaggle 4x L4, TP4 | 26B-A4B | 7 | 2 (221) | 14.1-15.1 | 2.1-2.2 |
| Kaggle 4x L4, 4 servers TP1 | E4B | 36 | 3 (213) | 30.4 (30.2-32.0) | - |
| RTX 5080 16 GB | E4B | 5 | 3 (339) | 88-90 | - |

Three readings. (1) **Concurrency matters as much as the GPU**: the scorer's own hardware is 2.0-2.3x slower per
session at 10 concurrent sessions than at one. (2) **Small changes move the factor**: serving a LoRA adapter cost 14-16% of
speed on the same GPU type, which would silently shorten a 7-minute budget to 6. (3) **Speed is stable within a setup**
(A100: +-4% over 15 runs) but **not across nominally equal ones**: two other E4B runs on the same RTX 5080 at the same
5 sessions ran at 24 and 40 tokens/s, for reasons the run metadata does not record. Calibrate every run, not every
machine. (E4B has no factor: we have no logged sequential E4B run on the scorer.)

### 4.2 Without normalization, the cap is a hardware setting

Same agent (g31_v9b), same 10 tasks, same nominal 4.5-minute cap. With 10 concurrent sessions on Kaggle 4x L4 at the
nominal wall cap (about 2.3 scorer minutes) it solved **4/10**; with the cap scaled to 11 minutes wall it solved **9/10**
(sibling g31_v9c: 10/10). That scaling assumed a factor of 2.5 from one spot check; the toolkit later measured 1.98 (CI
1.84-2.24) for the run, so 11 minutes was 5.6 scorer minutes, not 4.5: a guessed factor is itself an error source. Another agent (g31_v11m) at the nominal cap solved 5/71 with 66 of 71 sessions
timing out. Each looked like an agent failure; each was a budget half the scorer's.

|---|---|---|---|---|

| RTX PRO 6000, 5 sessions | 0.84 | 6.0 min | 19 | 15 |
| Kaggle 4x L4, 10 sessions, converted | **[L4]** | 15 min | **[L4]** | **[L4]** |

The RTX PRO 6000 run differs from the reference by 2 tasks, about one pooled SD (Section 5): consistent with no effect.
**[L4]** tests the conversion where it matters, at a factor of ~2, and its unconverted twin measures the error.

### 4.4 Why one factor works here (and where it would not)

| Check (54 full runs) | Value |
|---|---|
| Model share of session wall time | 0.965-0.997 (every run) |
| Prefill share of model time (fitted) | median 2.7%, max 5.5% |
| Fit R^2, per-call time model | median 0.987 (min 0.81) |
| Late / early calls, tokens/s (single-GPU, 5 sessions) | 0.97-1.05 |
| Late / early calls, tokens/s (4x L4, 10 sessions) | 1.03-1.27 |

Sessions are model-bound: ~3,400 shell commands in six runs had a median under 0.1 s and a 99th percentile <= 8 s.
Prefill is small because prefix caching leaves each call only the tokens added since the previous one. Decode speed
barely changes as the context grows on a lightly shared GPU. The exception is heavy sharing: at 10 concurrent sessions
late calls run up to 27% faster than early ones, because sessions finish and free the GPU; a run-level factor then
under-converts the start of the run and over-converts the end. Contrast TraceLab's frontier-model sessions, where tool time rivals generation: there a decode factor would convert only
part of the budget, and `timing` would flag the sessions.

## 5. Noise

### 5.1 Local runs

Full runs of the same configuration on the same 55 tasks (strict grading, scorer-speed caps):

| Config | Solved per run | Setup |
|---|---|---|
| g31_v12 | 20, 19 | A100 |
| g31_v12d | 20, 18 | A100 |
| g31_v9d | 19, 19 | A100 |

| g31_v9c | 15, 13 | RTX PRO 6000 (converted) |
| g31_v15 | 19, 21 | RTX PRO 6000 (converted) |

Pooled run SD **1.19 tasks** (6 configs, 6 degrees of freedom); task-level SD **1.61 tasks**; 4-8 of 55 tasks flip
between identical runs. With the larger estimate: one run each ranks a true 2-task margin wrongly **19%** of the time
(11% with two runs each), a 1-task margin **33%**; detecting a 2-task margin with 80% power takes **11 runs** per agent.
Runs on different hardware enter the same pool only because they were converted to scorer minutes; the converted
v12e pair (17 / 19) is no further apart than identical runs on one machine. A smaller model is noisier: Gemma 4 E4B
solved 12 and 8 of 71 tasks in two identical runs.

### 5.2 The leaderboard

Public scores are single draws on ~58 hidden tasks. Community resubmissions of identical files vary with an SD of
1.4-1.8 tasks [D. Afshar, Kaggle notebook; competition forum]: one bundle that scored 13/58 (0.22) drew 7 and 9 when resubmitted by others,
and the most-rerun public configuration scored 8-11/58 over 7-10 draws. Our own resubmission of that 0.22 notebook
scored 9/58 (0.15). With SD 1.6, one draw's 95% interval spans about +-3 tasks (`scorer-minutes draws --sd 1.6 --score
9`: 5.9-12.1). Our g31_v12e and g31_v9c ranked one way locally (17-19 vs 13-15 of 55) and the other way publicly (0.06
vs 0.12, ~3.5 vs ~7 of 58); with these SDs the public reversal says little about either agent.

## 6. Protocol (one page, for anyone reporting time-budgeted agent results)

1. **Log every model call** with start / end timestamps and token usage (any OpenAI-style client can).
2. **Measure the reference speed** on the scoring setup at its real concurrency (`calibrate --reference`), not at the
   concurrency you develop with.
3. **Calibrate every run**, not every machine: set the wall cap to `budget x f`; report f with its CI.
4. **Check the assumption** (`timing`): model share, prefill share, late/early ratio. If flagged, convert only the model
   share, or measure on the scorer.
5. **Report budgets in scorer minutes**, plus sessions at the cap and the projected total time.
6. **Run every configuration at least twice**; report each run, the mean and the pooled SD (`noise`); consult the
   runs-needed table before claiming a margin.
7. **Read a single leaderboard draw as an interval** (`draws`), not a rank.

## 7. Limitations

* **Heavy concurrency makes speed drift within a run** (late/early up to 1.27 at 10 sessions); a run-level factor is an
  average. Single-session or lightly shared setups do not drift (0.97-1.05).
* **One model family, one harness, one task source** (Python repositories). Tool-heavy agents (long builds, test suites)
  are less model-bound; `timing` detects this, but the single factor would not apply.
* **The direct scorer anchor has 5 sessions**; our development reference (A100) is 6-10% slower than it. Both are
  reported; more sequential sessions on the scorer would tighten the anchor.
* **Noise estimates rest on six repeated pairs**; the task-level SD uses all 55 tasks but assumes tasks are independent.
* **Leaderboard noise is partly community-reported**; we add our own resubmission.

## 8. Conclusion

A wall-clock cap is a hardware setting unless it is converted. One measured factor, checked against the logs it comes
from, makes local results comparable to the scorer's; reporting run noise keeps one- or two-task differences from being
read as progress.
